## 二、产品定位与目标

### 2.1 一句话定位

知隙是一款面向不同学习者的知识检验助手：用户提供自己已经学习过的资料时，知隙自动提取知识点并生成待办清单，结合重要程度和掌握情况主动提问、追问，通过资料和外部依据进行反馈。模拟面试也可以仅根据用户设置的岗位和场景直接开始。

### 2.2 目标用户

面向有自我检验需求的人，不限定专业、行业或年龄，例如：

- 学生：检验自己对课程资料、复习笔记或知识点的理解。
- 自学者：根据书籍、笔记或其他资料进行回顾与自测。
- 求职者或职场人士：围绕准备过的内容进行口述练习和模拟面试。

以上只是例子，不作为限定用户群体或首版支持学科的承诺。

### 2.3 核心目标

1. 让用户以自己的学习资料为主要范围，检验是否能够理解和表达相关内容。
2. 以知隙主动发起问题和追问为主要交互方式，同时允许用户主动提问、指定重点和调整过程。
3. 给出能够回溯用户回答、资料原文和外部来源的判断依据。
4. 对证据不足、不同表达和开放性问题保持审慎，允许用户纠正判断。
5. 将知识点组织为待办清单，按重要程度和用户表现动态安排检验，清晰展示完成进度。
6. 为每个知识点设定追问上限和完成标准，避免持续循环；支持模拟面试，并为后续复查与复测保留记录。

**边界**：知隙以检验已有学习成果为主要用途。解释问题、说明判断依据和应用户请求进行讨论可以支持，但系统性讲课或替用户制定学习课程不是本轮确定的核心目标。

### 2.4 衡量价值的方向

建议通过真实使用和人工核对检验以下问题，而不预先声称产品已经达到某种学习效果：

- 问题是否围绕用户选择的资料和目标。
- 追问能否帮助澄清用户的回答。
- 评价是否准确反映用户所说的内容，并能提供可复查的依据。
- 用户能否区分资料内的内容、外部核验信息和尚待确认的问题。
- 用户能否依据记录再次检验之前不明确的知识点。

### 3.2 本文采用的建议和假设

以下内容用于让方案可讨论，尚不是最终决定：

- 默认以用户选择的资料和范围组织问题；用户可选择是否使用资料外拓展题，默认开关状态及具体呈现方式待确定。
- 先检索用户资料，在必要时联网补充核验；来源不一致时分别展示。
- 日常检验的语音输入、语音播报和面试实时语音已确定为需要支持的能力；各能力进入首版的先后、服务选型及实时交互细节仍需确定。
- 使用 RAG 或其他适合资料规模的检索方式提供上下文，先不强制引入知识图谱。
- 资料和检验结果保存在用户本机；用户已委托设计本地目录、备份恢复、删除和音频保留策略，本文给出建议默认值供后续验证。

### 3.3 用词约定

- **上传资料**：用户向知隙提供资料，可能是选择本地文件等方式；该词不预设文件一定上传到远程服务器。
- **资料依据**：来自用户提供资料的相关内容及可定位来源。
- **外部依据**：通过联网检索并核对的公开来源。
- **回答依据**：用户本轮实际说过或提交的内容。
- **盲点**：某个知识点存在尚未解释清楚、与现有依据有出入或需要进一步确认的情况，不等同于对用户整体能力的定论。
- **检验范围**：本轮选择的资料、章节、主题或其他边界；未检验的内容不能被判定为已掌握。
- **知识点待办清单**：从所选资料中提取、供用户查看和调整的知识点集合；每个知识点应能作为相对独立的检验对象。
- **知识点的一次检验**：围绕同一个知识点提出 1 个主问题，并在需要时提出最多 2 次追问；它不同于包含多个知识点的整轮检验。
- **必备要点**：针对某个知识点，在出题前根据资料列出并可供核对的必要内容。它们用于判断本次回答覆盖情况，不代表系统已完整识别整份资料。
- **回答处理回合**：从用户提交一次文字回答，或实时口述的一次发言结束后启动处理开始，到系统返回反馈或下一问题结束的处理过程；该回合内的模型、工具调用和耗时受到独立预算限制，不是对整个实时面试时长的限制。

## 四、主要使用场景

### 场景 S01：根据资料主动检验

用户提供资料并选择或确认检验范围。知隙自动提取知识点并生成待办清单，根据重要程度和用户表现安排问题；回答后结合资料检索结果评价，必要时在追问上限内继续澄清，完成的知识点移入已完成记录。

### 场景 S02：用户主动调整或提问

检验过程中，用户可以围绕当前知识点要求调整难度、重新解释问题，或者询问某条判断的资料依据。用户不能中途自由切换到其他知识点或主题，但可以退出当前主题并保留进度。

### 场景 S03：联网核验补充内容

用户的回答包含当前检索结果没有覆盖的内容，或资料与其他信息可能存在冲突。知隙按需使用联网工具查找来源，核对后区分资料依据与外部依据；找不到充分依据时保留不确定性。

### 场景 S04：模拟面试

用户设置所需的面试或口试场景，可以选择已上传资料，也可以不提供资料直接开始。知隙连续提问，并根据回答追问；结束后结合实际回答与可用依据提供复盘。求职面试、课程口试等场景的侧重点可以不同。

### 场景 S05：复查与复测

用户回看之前的检验记录和待确认内容，选择某个知识点再次检验。新的结果与旧记录关联，仅反映本次覆盖的问题及回答。

## 五、功能需求

以下列出已确认的功能规则及建议细化。能力方向是否已确认，以第三章和各功能中的状态标记为准；未明确确认的具体交互与首版取舍仍需讨论。

### F01 资料提供与处理

**目标**：让用户提供学习资料，并知道哪些内容可以被检验。

**已确认**：首版接收 Markdown、PDF 和 Word 文档，每份文件不超过 10 MB；支持扫描版 PDF，以及文档中的图片、表格、图表和公式，采用 MinerU 参与文档解析。Word 的 .doc 与 .docx 均作为支持目标，具体兼容性须按选定版本实际验收。

需求与建议：

1. 支持用户选择资料，对每份文件检查 10 MB 限制，显示资料名称、处理状态和失败原因；多文件总量上限及 MB 的具体字节计量待实现时明确并在界面说明。
2. 使用 MinerU 处理需要解析的 PDF、Word 等文档；Markdown 可直接读取后进入知识提取和检索流程，不要求为了使用 MinerU 而重复转换。
3. 支持文档中扫描文字、公式、表格、图表和图片的提取与处理，保留可核对的原图或原页定位。提取图片文件本身不等于正确理解图表或图片含义；对无法可靠识别或理解的部分应提示用户核对。
4. Markdown 若引用同目录或用户授权目录中的本地图片，应用应能够读取相关图片；图片缺失或不可访问时明确提示。首版不额外开放独立 PNG、JPG 等图片文件上传；批量附图限制及远程图片引用策略待设计。
5. 默认处理所选文档的全部内容；若用户选择页码范围，或因工具版本、页数限制、异常而只处理部分内容，必须明确显示范围和未处理部分，不能宣称整份文档已完成。尤其应检查所选 MinerU 调用方式是否存在默认页数限制。
6. 将处理失败、部分成功和处理完成区分展示；提取可用于检验的内容，尽量保留文件、章节和页码等可用定位信息，允许用户选择本轮使用的资料、章节或主题。
7. 文档解析在本机后台进行，提供进度、取消与失败反馈；可限制并发、CPU 或其他资源占用，避免解析任务阻塞界面。取消后的部分结果应标明未完成。后台运行也可能因机器资源不足而造成卡顿，响应性及速度需要在目标机器实测，不能仅凭文件不超过 10 MB 保证。
8. 资料更新后的记录如何关联原始版本，需要在设计阶段明确。MinerU 版本、模型文件、安装包大小、CPU／GPU 兼容性和运行资源需要实际验证。

**解析质量验收方法**：

- 建议首轮准备至少 20 份覆盖 Markdown、Word、可选中文字 PDF、扫描 PDF、公式、跨页或复杂表格、文档内图片及图表的代表性样例，包含超过 10 页和接近 10 MB 的文件；人工对照原文标注作为参考答案。样例数量是初始建议，不代表能保证覆盖全部情况。
- 文字可以按约定的字符归一化规则统计字符错误率：替换、遗漏和多出字符数之和除以参考文字字符数；无可比文字时不计算该项。
- 公式以人工核对的等价结果统计错误或未识别公式占参考公式的比例；表格分别检查是否遗漏，以及单元格内容、行列与合并关系的错误情况。
- 对图片和图表分别检查是否提取、来源定位是否可追溯，以及相关文字、关键数据或含义是否正确处理；无法判断的内容不能默认为正确。
- 对照原文检查漏页、阅读顺序及来源定位，并记录各类错误、漏检和不能评价的样例。最低通过阈值需要在获得样例与实测结果后确定，不能先假定 MinerU 几乎没有错误。

**待确认**：各类错误率或准确率的具体通过阈值、样例规模、多文件总量和附图大小限制。

### F02 知识点待办清单与动态提问

**已确认**：知隙从用户选择的资料中自动提取知识点，生成待办清单，并根据重要程度和用户掌握情况主动安排检验。

1. 每个知识点应能查看名称、资料来源、重要程度、当前状态，以及相关的问题、回答和判断依据。来源定位按实际解析结果展示，不编造章节或页码。
2. 用户可以查看和调整清单，例如修改名称、补充、合并或排除知识点；不要求用户必须逐项确认后才能开始检验。清单及范围改变时应明确当前检验范围。
3. 知隙动态安排提问顺序，综合考虑知识点重要程度、用户指定的目标和当前回答表现；重要性判断不应仅依赖资料中出现的次数。尚未检验不等于不会，也不等于已经掌握。
4. 提问应能关联资料依据，并可根据知识点检查理解、解释或应用，不只比较原文措辞。安排顺序应兼顾尚未检验的内容，避免持续追问少数知识点而遗漏其他项目。
5. 每个知识点的一次检验包含 **1 个主问题、最多 2 次追问**，最多对应 3 次正式作答；证据充分时可以提前完成，不必凑满次数。每次只提出一道检验问题，不得通过合并多道独立题目绕过上限。
6. 到达追问上限后，结束该知识点的本次检验：未满足完成标准的知识点保留为待巩固或待确认，系统转到同一主题的下一知识点；如果没有其他可检验知识点，则结束本轮并显示仍待处理的内容。同一轮不得自动重置次数并反复检验同一知识点。用户之后主动选择重新检验时，可开始一次新的检验并重新计数。
7. 请求重述题意、模型或工具失败后的同一回答重试，不应被当作新增追问或新增正式作答；用户跳过、表示不会和提前结束应分别记录。
8. 通过完成标准的知识点移出待办主视图，进入可回看的已完成记录。跳过、待巩固和待确认都不算已掌握；清单进度与清空条件见 F09。
9. 用户可选择启用资料外拓展题；资料内问题、资料外拓展题及无资料面试中的模型生成问题应明确区分来源。整轮题目总数不固定，旧版的“五个主问题”不是本次默认规则。

知识点清单可能遗漏、重复或拆分不合理；资料解析或清单提取不完整时，应说明未处理范围，不能将清单宣称为整份资料的完整覆盖。具体排序算法和重要程度的计算方式待设计与验证。

**“外部拓展问题”的含义**：回答这类题目必须使用所选资料没有覆盖的知识。例如资料只介绍质数的定义，进一步询问质数在密码学中的应用，就属于资料外拓展；用不同措辞或新例子检验资料中已有的定义，并不必然是外部拓展。

**题目与依据溯源**：记录题目所属类别、对应资料片段及可靠页码或章节，或外部来源的标题、链接、可获得的时间和支持内容；多来源时分别关联。无可核实来源的模型生成内容须标记“未找到可核验来源”，不能伪造引用或作为已核实事实。来源与答案何时向用户展示可按日常检验和面试场景设计，但不能因展示方式泄露面试答案。

用户是否启用外部拓展题与联网补充核验是两个不同开关或决策：未启用拓展题时，按需联网核验资料或用户回答仍是允许的。开关默认值与作用范围待确定。

### F03 对话与主动权

**目标**：保持知隙主动检验，同时让用户能够参与和控制。

建议需求：

- 知隙可以主动提问，根据回答决定是否追问。
- 用户可以直接提问、要求解释题意或判断依据，也可以主动退出当前主题；面试模式不提供作答提示和临时知识解释。
- 日常检验和面试均不允许用户在当前主题未完成或未退出时自由切换到其他知识点、主题、资料或项目。完成或主动退出当前主题后才可切换；退出应保留未完成进度和已接受回答，不能标记为已掌握。
- 当前知识点达到完成标准时，知隙按清单自动安排下一项；即使达到追问上限仍未掌握，也应结束该知识点的本次检验，标记待巩固或待确认，并自动进入同一主题的下一项。这是系统按流程推进，不属于用户中途自由切换。
- 日常检验支持提示和临时解释；用户使用后需保留“使用提示”或“接受临时解释”的痕迹，并将对应知识点标记为“不熟练”、待独立验证。之后可以在追问限额内通过不同问题独立验证，不得仅将对提示的复述算作独立掌握。
- 用户请求解释时，可以围绕已有资料和检验依据作答；不要求每次对话都转变为教学课程。面试不提供提示和临时知识解释。

退出后重新打开原主题时，应能恢复已保存的未完成进度；具体交互及重启恢复方式待设计。

### F04 回答评价与盲点

**目标**：评价用户的实际回答，而不是只比较是否包含预设关键词。

**已确认的完成标准**：

1. 在出题前，根据相关资料为该知识点列出可核对的必备要点及来源；若要点范围过大，应拆分知识点或先澄清范围，用户可以查看和纠正。无用户资料的面试可先依据岗位与场景生成候选问题和要点；需要客观核验时应取得适用依据，依据不足则保留待确认，不能伪称来自用户资料。
2. 必备要点覆盖率 = 用户在本次检验中独立、正确说明的必备要点数 ÷ 事先列出的必备要点总数。主问题与追问中的独立回答可以累计；必备要点为空或来源不足时，不能计算为 100%，应标记待确认。
3. 覆盖率达到 **100%**、没有尚未澄清的关键错误，且资料或可靠外部来源足以支持判断时，标记该知识点为“本轮已掌握”。该指标只表示预先列出的要点在本次回答中的覆盖情况，不是整个学科的客观掌握百分比。
4. 用户使用不同措辞表达同一意思时应按语义评价，不应仅因缺少关键词判错；开放性问题允许多种有依据的合理观点。
5. 日常检验中使用提示或接受临时解释，应记录辅助痕迹，并将对应知识点标记为“不熟练”、待独立验证。知隙直接给出某个答案后，用户仅复述该答案不能直接算作对该要点的独立掌握；可在剩余追问额度内用不同问题验证，通过后可以更新状态，但辅助痕迹仍保留。
6. 回答未覆盖全部要点时，可在追问额度内继续澄清；达到上限后结束本次检验。资料证据不足、来源冲突尚未解决或系统无法可靠判断时，标记待确认，不强行判为已掌握或不会。
7. 评价应区分已说明、未说明、有出入和证据不足，展示用户原回答及资料或外部依据，并允许用户补充、提出异议或纠正。用户主动表示不会与跳过应分别记录。

上述覆盖率依赖必备要点提取和模型判断的质量；即使达到阈值，也只反映本次已检验范围内的结果，不保证对未覆盖内容或长期保持情况的判断。

### F05 资料检索与证据展示

**目标**：使问题和评价可以回溯到资料与用户原回答。

建议需求：

- 在出题和评价时，获取与当前任务相关的资料内容；内容较短时可直接使用完整上下文，较长时可使用检索增强生成（RAG）。
- 展示资料来源和相关内容，并在可靠获取时显示章节、页码或其他定位信息。
- 将“资料原文”“用户回答”和“系统的判断解释”区分开。
- 引用应能够对应实际来源；无法定位时不要编造页码、原句或出处。
- 本轮没有检索到依据，不等同于已经确认整份资料没有相关内容。
- 单纯展示引用不能证明判断一定正确；资料解析、检索、模型理解和引用关系均需验证。

### F06 联网搜索与外部核验

**已确认**：由项目自行实现联网搜索工具，并提供开启、关闭控制；Agent 可以按需用该工具对资料或回答进行外部核验。

建议需求：

1. 为 Agent 提供联网搜索能力，并在需要时读取来源正文；搜索工具被关闭时不得调用。建议提供全局开关及单次会话开关，具体默认值待确认。
2. 在资料依据不足、用户要求核验、资料可能过时或来源存在冲突时，Agent 可以决定是否调用工具。
3. 搜索结果应作为待核对的候选来源；不能仅凭搜索结果标题或摘要就宣称核验完成。
4. 优先考虑与问题适用条件相符、来源可核实、具有适当权威性和时效性的资料。
5. 明确标注每项依据来自用户资料还是外部来源；外部来源应有可打开的链接及可用的标题、时间等信息。
6. 资料与外部来源不一致时，呈现差异和适用条件；无法判断时保留待确认状态。
7. 搜索失败、网页无法访问或未找到可靠来源时，应明确说明，不能伪造链接、正文或核验结果。
8. 外部核验不自动改变用户原始资料。是否将外部资料保存为新资料，由后续交互设计确定。
9. 自行实现搜索工具不预设自行建设搜索引擎；搜索数据来源、服务接口、费用和离线失败处理另行选型，不表示已经接入任何外部搜索服务。

**数据源可选方案，尚未定案**：

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 外部搜索 API | 自己实现工具和统一适配接口，后端可接入 Tavily、Brave Search 等服务。 | 接入相对直接，但需要实际比较中文效果、国内网络可用性、密钥、额度与费用，不能假设模型密钥可以用于搜索。 |
| 自部署聚合搜索 | 自行部署 SearXNG 等聚合服务，通过工具访问。 | 更可控，但需要额外运行和维护组件；它仍会向配置的外部搜索引擎发送查询，也可能受限流或不可用影响。 |

建议先设计统一搜索接口，选定一个可用数据源实现；服务商和密钥由谁提供、费用如何承担，均待确认。搜索关闭、未配置或服务不可用时，清楚标注未联网；有足够本地依据仍可继续检验，缺少依据时标为待确认，不能伪造核验结果。

### F07 模拟面试与口试

**已确认**：面试可以使用已有资料，也可以不上传资料，根据岗位与面试场景直接和 AI 问答。面试过程中不提供提示和临时知识解释。

- 用户可以设置岗位、面试或口试场景、主题和重点，并选择是否使用已经上传的资料。
- 知隙连续提问，并根据用户回答选择追问。
- 用户可以结束对话并查看复盘；复盘应关联实际问题、回答和可用依据。
- 客观知识可以结合资料及外部来源核验；经历、观点和开放性表达应说明评价角度，不冒充唯一标准答案。
- 不上传资料时，不得伪称题目或评价来自用户资料；可根据用户设置的岗位与场景组织问答，并清楚区分模型生成内容与可核对的外部依据。
- 面试中遵循 F03 的主题切换限制；评价何时出现以及是否需要评分，待确认。

### F08 语音输入与语音对话

**已确认**：日常检验支持语音输入和语音播报；日常检验不提供实时语音对话。实时语音对话仅用于模拟面试。

需求与待确认细节：

1. 语音输入：录音后转换为文字，可供用户确认、修改和提交；每次是否必须确认待确定。
2. 语音播报：将知隙的问题或反馈读出，与语音输入结合后形成轮流对话。
3. 面试实时语音：支持面试场景下的实时语音交流；实时语音不同于单纯的录音转文字和逐段播报。是否支持打断、自动判断说话结束，以及时延指标需要单独确定。
4. 文字输入与文字记录可作为补充交互方式。
5. 如果语音识别或播报使用外部服务，应向用户说明相关数据会发送给相应服务；音频是否保存、保存多久需另行确定。

上述三类能力属于已确认需求，但分别进入首版或后续版本的时间，以及模型或服务的具体选型，尚未确定。

**语音服务方案，尚未定案**：

| 方案 | 说明 | 取舍 |
| --- | --- | --- |
| 外部语音服务 | 日常分别接入语音识别和语音合成；实时面试接入支持实时语音的接口。 | 接入较直接，但音频需要发送给服务商，可能产生费用；文本模型 API 和实时语音接口不一定相同。 |
| 本地语音模型 | 在用户设备运行识别、合成及所需实时处理能力。 | 有利于本地处理，但增加安装包、模型文件与 CPU／GPU 负担；能否达到可用的实时体验需要实测。 |
| 混合方案 | 日常语音与面试实时语音分别选择本地或外部服务。 | 用户可按网络、性能与隐私选择，但配置和维护较复杂。 |

建议先评估外部服务完成首个可用版本，再根据设备测试决定是否增加本地或混合方案；这是建议而非已选供应商。是否支持打断、具体时延与哪些能力进入首版仍需用户确定。

### F09 检验记录、纠错与复测

**目标**：让用户清楚待办进度，回看知识点的检验依据，并在需要时再次检验。

**已确认的清单与完成语义**：

- 知识点至少应能区分未检验、检验中、不熟练、待巩固、待确认、待复测、暂时跳过和本轮已掌握；未检验、跳过或系统判断未完成不等同于不会或已掌握。提示和临时解释需要单独保留痕迹。
- 记录所选范围、知识点、重要程度、事先列出的必备要点、问题、回答、追问次数、评价、资料依据和外部来源。已完成项目移入可查看的记录，不因移出待办视图而删除。
- 用户可以对知识点或评价进行纠正、补充，并保留可理解的历史关联；可以选择某条记录或知识点发起新的检验，新问题和新回答独立记录。
- 当前清单的完成进度可按“本轮已掌握的知识点数 ÷ 当前检验范围内的知识点总数”展示；总数为 0 时不显示 100%。该比例是清单进度，不是对用户整体能力的百分比评分。
- 只有当前检验范围内至少有一个知识点，且所有知识点都按 F04 达到“本轮已掌握”，才能显示清单已完成。不熟练、待巩固、待确认、待复测、检验中或暂时跳过的项目不能算作完成；筛选视图为空也不能触发完成提示。
- 提示语限定为“当前范围内的知识点均已达到本轮检验标准”。用户调整范围或排除项目时，应明确显示实际范围及被排除的数量；解析或提取不完整时，应说明未处理范围，不能宣称整份资料已经掌握。
- 已接受的用户回答应在处理中断、模型失败或预算耗尽后保留；支持用户回看，并在可行时基于原回答重试，具体持久化与恢复机制待技术设计确定。

已接受回答的保留是上述基本要求；记录和总结的呈现形式、其他数据的保存策略仍需确认。定时提醒按用户决定暂缓，何时纳入另行确定。

### F10 Agent 工具与执行边界

**目标**：让 Agent 使用工具支持检验，实际工具权限由应用控制。

建议至少考虑以下工具能力：

| 能力 | 建议用途 |
| --- | --- |
| 资料检索 | 根据问题或回答查找用户选定范围内的内容与来源。 |
| 联网搜索 | 获取可能相关的公开来源。 |
| 网页读取 | 核对来源正文；若选用的搜索工具已提供可核对内容，可按其能力设计。 |
| 检验记录 | 由应用登记问题、回答、依据和评价；实际写入权限和调用方式待技术设计确定。 |

Agent 可以提出工具调用并使用结果继续检验；应用应限制可调用工具、允许访问的资料范围和工具参数。用户资料和网页内容属于待分析数据，不能自动获得修改系统规则或扩大工具权限的能力。

**回答处理回合的默认执行预算**：

| 预算项 | 初始上限 | 计数范围 |
| --- | --- | --- |
| 模型调用 | 4 次 | 处理同一次用户回答的模型请求总数；失败的请求也计入。 |
| Agent 工具调用 | 5 次 | 包括资料检索、联网搜索、网页读取等；失败的调用也计入。用于保存用户回答和运行状态的应用内部持久化不依赖剩余的 Agent 工具预算。 |
| 联网搜索 | 2 次 | 计入上述 5 次工具调用，而不是额外增加的额度。 |
| 回合总耗时 | 60 秒 | 从用户提交文字回答，或一次实时口述结束后开始处理，到返回反馈或下一问题为止，包含模型和工具处理时间。 |

以上是已讨论的可调整初始值，并非经过实测得出的最优配置；是否提供用户侧配置入口待确定。

当调用次数已用完而判断仍需更多请求，或达到时间上限时判断尚未完成，应停止派发超出预算的模型与工具请求，保留已接受的回答和执行状态，并明确提示本次判断未完成或证据不足；不能将系统超时或预算耗尽直接判为用户不会或已掌握。若已在预算内获得充分结果，则正常返回，不能仅因恰好用完额度就判为失败。可允许用户手动基于同一回答发起新的处理尝试，不增加追问或正式作答次数。

对于无法立即取消的外部请求，应用应尽力取消并阻止迟到结果覆盖已经结束或更新的状态；60 秒是该回合的处理预算，不保证所有外部服务都会在截止时实际停止运行。

面试实时语音可能是一段持续的交互连接；上述 60 秒是单次回答处理回合预算，不应被解释为整场面试或实时音频连接的总时长。实时语音的响应延迟及其中工具调用的具体协调方式待设计和验证。

### F11 用户配置模型服务

**已确认**：用户通过应用界面自行配置模型服务，由软件负责管理配置，不要求用户手动编辑配置文件。

- 界面提供服务商、模型名称、Base URL 和 API 密钥等输入项，并支持保存、修改与选择配置。
- 建议支持连接测试和明确的错误提示；如需支持多套配置、更多协议参数或模型能力选择，具体交互待确定。
- 普通配置记录和 API 密钥的存储方式应区分；密钥必须加密保存。Windows 首版建议使用当前用户范围的 DPAPI 或等效安全凭据存储；加密不可用时应明确报错，不回退为明文。密钥不以明文写入普通项目资料、日志或导出文件。
- 必须提醒用户定期检查 API 密钥。建议默认每 90 天在应用启动时提示一次，用户可以修改周期或关闭提示；提示仅提醒用户检查，不自动宣称密钥已过期、被泄露或已轮换。应用未运行时不保证准时提醒。
- 该提醒是本地 API 密钥检查需求，不恢复此前暂缓的一般学习定时提醒或云邮件调度。
- 不同服务商的协议和模型能力可能不同；能填写这些字段不等于所有接口自动兼容。需要明确首版支持的服务商、接口协议、工具调用与语音能力，并通过实际联调验证。

### F12 Markdown 总结与导出

**已确认**：保留 Markdown 总结，并支持导出 HTML、Markdown 和 PDF。

- 基于检验内容自动生成真实、可编辑的本地 Markdown 总结文件，关联知识点、回答、判断和可用来源；可支持用户手动触发，具体自动生成时机与编辑交互待确定。
- 用户可导出以上三种格式；导出的对象、文件位置、中文及代码和表格的排版要求需在详细设计中确定并验证。
- Word 是首版资料输入格式，当前确认的导出格式不包含 Word。

### F13 记忆与提示词

**已确认**：保留记忆，并提供系统提示词、项目提示词和个人提示词三类内容。系统安全规则优先；在安全边界内项目提示词可覆盖个人提示词，项目之间隔离。

- 记忆用于保留对后续检验有帮助的信息，应支持用户查看、编辑和删除；具体记忆范围、自动提取和确认方式待确定。
- 按系统安全规则、项目提示词、个人提示词的优先顺序处理；项目提示词只影响所属项目，用户个人提示词可供各项目使用，具体加载、合并与版本记录方式待设计。
- 系统安全规则不得被项目或个人提示词覆盖；建议将不可由低优先级内容更改的安全基线与可配置的教学风格区分，系统提示词的界面编辑范围待确认。
- 记忆或指令发生实质冲突时，生成包含双方内容、适用范围和来源的冲突候选，交由用户处理；处理前不得静默覆盖或合并已有长期内容。对于当前项目内项目提示词与个人提示词的冲突，本轮执行在系统安全范围内按项目优先，同时展示候选并由用户处理持久内容；无法安全判断时请求处理或保留未决。
- 不同项目各自成立的不同设定应隔离保存，不自动合并、互相覆盖或泄露；跨项目复制或将经验提升为个人级内容需要用户明确选择。
- 日后可以讨论由用户设定规则自动解决记忆冲突；首版不将尚未确认的冲突自动改写为长期记忆。
- 参考 Claude Code 分开保存长期指令和可审阅记忆的思路，但不宣称完全复制其内部实现。系统提示词可以降低被误导的风险，却不能单独保证防注入；资料、网页和工具结果作为非可信数据，文件与网络等权限由应用独立校验和执行。

### F14 自进化与 Skill 沉淀

**已确认**：保留自进化，让系统积累可复用的 Skill，改进后续检验或面试流程。

- 可将经核实的反馈、问题或有效流程整理为 Skill 候选，记录来源、适用场景及拟改变的行为；例如某类知识点的追问方法或判断步骤。
- 沿用此前讨论的控制原则：候选需要经过验证和人工确认后启用，记录版本，支持停用或回退。具体验证样例、作用范围和交互方式待确定。
- 自进化在此指沉淀和调整可复用的行为指导或流程，不自动表示对基础模型进行参数训练；实际效果需通过对照验证，不能仅凭模型自评宣称改善。
- 对外部 Skill 的兼容格式、所附脚本的执行环境和权限，以及是否采用 Agent Skills 的文件规范，需要单独设计。

**可选方案，尚未定案**：

| 决策项 | 方案与建议 |
| --- | --- |
| 验证样例 | A：至少 20 条人工核对样例，区分开发与验收集，延续此前基线；B：使用 50 条或更多覆盖不同主题和难度的样例，人工成本更高。样例数量不是效果保证；需同模型配置对照目标改善和既有样例退步。 |
| 生效范围 | A：先在当前项目启用，建议作为初始选择；B：经用户明确确认后提升为个人级 Skill。不同项目的数据不能因共享 Skill 自动混用。 |
| 外部格式 | A：参考 Agent Skills 的 SKILL.md 及可选参考文件，优先验证纯文本 Skill；B：兼容更多自定义格式与脚本，灵活但运行环境和权限更复杂。是否运行外部脚本须单独控制。 |
| 外部 MCP 接入时机 | A：先完成内置检索、联网与自进化基础流程，随后接入外部 MCP 和 Skill；B：首版同时接入，范围更大。具体版本安排由用户选择。 |

### F15 外部 MCP、Skill 与其他工具

**已确认方向**：后续支持用户接入外部 MCP、Skill 和其他工具；首版范围及具体接入方式待确定。

- MCP 可作为接入外部工具、资源和提示模板的一种协议；外部 MCP 服务器可以提供工具或提供访问 Skill 内容的能力，但连接 MCP 并不自动获得通用的 Skill 管理和执行机制。
- Skill 是可复用的任务指导与相关资源；一种公开格式使用 SKILL.md 和可选的脚本、参考资料等。知隙需要自行确定如何发现、加载、授权、启用和管理不同来源的 Skill。
- 外部工具和 Skill 是否启用、可访问哪些资料与网络资源，应受用户配置及应用实际权限约束；在回答处理回合中执行的 Agent 工具调用仍需计入 F10 的预算。

### F16 回答时间与检验指标

**已确认**：记录并展示用户的回答时间；不以回答快慢单独断定掌握或不熟练。

- 为每个主问题及追问分别记录用户作答时长，并可汇总到对应知识点；AI 处理、联网检索和等待模型反馈的时间单独记录，不混入用户作答时间。
- 建议文字题从题目展示完成计到用户提交；语音题从题目播报完成计到用户结束发言。若用户在播报时打断，应从实际开始回答时计时并标记该情况；异常中断和是否排除主动暂停的处理待设计。
- 语音时间包含实际说话时长，不能与文字输入速度直接比较；不设置“越快越好”的统一分数。
- 既有指标继续保留：必备要点覆盖率、清单完成进度，以及提示或临时解释的使用痕迹。
- 建议在结果中提供本轮总时长、追问次数和独立／辅助作答次数作为可解释的辅助统计；是否全部展示、是否需要总分或其他指标，尚待用户选择。

## 六、资料、来源与数据原则

### 6.1 资料和网络来源如何参与判断

1. 所选资料用于确定本轮主要检验范围。
2. 资料内容是判断的重要依据，但资料本身也可能存在错误、过时或不同版本。
3. 外部资料可以补充核验，也可能与用户资料相冲突。
4. 系统应分别呈现来源及各自支持的结论，不因某个来源被检索到就自动将其视为绝对正确。
5. 无法获得足够依据时，保留不确定性并允许用户继续补充。
6. 资料原文、用户回答、来源链接、检验结论之间应保留可追溯的关联。

### 6.2 数据与隐私

**已确认**：知隙以 Windows 桌面安装包交付，主要服务随应用在用户本机运行，资料、检验记录及其他业务数据保存在本机。

以下为进一步的产品要求与建议：

- 用户应能理解资料、回答、语音和搜索词分别会发送给哪些服务。
- 联网搜索应尽量使用完成检验所需的最少信息，避免直接把完整私人资料或回答作为搜索词。
- 可对用户资料、记录和工具的访问范围进行约束；网页和资料里的指令性内容不应自动获得工具权限。
- 检验记录、资料和音频的本地保存目录、查看、删除、导出、备份恢复与保留时长需要明确规则。
- 如果使用远程模型、联网搜索或其他远程服务，完成任务所需的上下文、搜索词或音频可能发送给相应服务；本地保存资料并不自动意味着所有推理和检索都离线。
- 模型 API 密钥应与普通配置和用户资料分开处理，避免写入普通日志或导出文件。

**本地数据与备份建议默认值**（用户委托设计，仍需按实际安装、空间和恢复测试验证）：

1. 数据建议默认位于当前 Windows 用户的 %LOCALAPPDATA%\Knowrift 目录，避免写入程序安装目录；界面展示实际路径。结构化业务状态可使用 SQLite，按用户空间和项目隔离，最终数据库布局待技术设计确定。
2. 选择导入资料时在应用管理的本地空间保留副本，并关联原来源；删除知隙内的项目或资料默认只删除应用管理的内容，不删除用户原路径中的原始文件。
3. 建议默认不长期保存原始音频，只保留本轮所需的临时音频与对话文字；用户可选择保存录音，建议默认保留 30 天并允许手动删除。具体实时处理中临时文件清理和外部语音服务的数据保留依其服务设置，不能由知隙单方面保证。
4. 建议应用运行时每日首次满足条件时在后台创建一次本机备份，保留最近 7 份，并支持用户手动导出备份至其他位置；备份应包含用户资料副本、检验记录、记忆、提示词与 Skill 等必要数据。
5. 数据库与相关文件的备份需采用一致性方案，检查备份是否完整；恢复前展示内容，允许恢复为新项目或在用户确认后处理冲突，不能静默覆盖现有数据。
6. 普通备份默认不包含 API 密钥和可重新生成的大型模型缓存；迁移到另一台机器后提示用户重新配置密钥，并按需要重建索引或准备模型文件。同一硬盘上的备份主要帮助恢复误操作，不等于应对硬盘损坏。
7. 用户删除项目时，界面应说明已有历史备份可能仍包含该项目，允许用户管理相关备份；自动清理策略和跨备份彻底删除方式需在实现前细化并测试。

### 6.3 安装与本机服务

- 用户通过下载安装包使用桌面应用，不以直接打开远程网页作为主要产品形态。界面具体采用何种桌面技术待确定。
- 业务后端、Agent 所需的本机服务，以及本地 MinerU 解析能力随桌面应用启动或受其管理；用户资料和检验结果默认保存在该用户的电脑中。
- 模型调用、联网搜索和未来可能接入的远程 MCP 属于按配置使用的外部能力，不改变主要业务服务与数据保存在本机的决定。
- 安装包需要解决应用及所需运行环境的安装、启动、升级和卸载，不要求普通用户自行配置全局 Java 或 Python。

**安装与测试可选方案，尚未定案**：

| 决策 | 选项与建议 |
| --- | --- |
| 运行环境 | 建议安装包提供所需 JRE、Python 和 MinerU 依赖，并评估将必需模型一并提供；代价是安装包较大，还需核对再分发许可和资源占用。 |
| 模型文件 | A：随安装包提供，初次解析不依赖下载，但包更大；B：首次使用时清楚提示并引导下载，包较小但依赖网络。具体选择及失败重试待确定。 |
| 干净环境测试 | 推荐使用 Windows 虚拟机快照或 Windows Sandbox，在未安装开发工具的环境测试安装、启动、升级与卸载；不同系统版本和 Sandbox 可用性需确认。 |
| 性能与硬件 | 虚拟机适合发现依赖遗漏，但不能代替真实电脑的性能和 GPU 测试。应在实际 Windows 设备上分别验证 CPU 模式及可用 GPU 模式、近 10 MB 复杂文档、界面响应和资源占用。 |

解析速度、峰值内存、CPU／GPU 负载、实际处理页数及界面响应应记录机器配置与测试数据；不能将官方示例或虚拟机结果当作所有用户的性能保证。

## 七、检索与技术架构

### 7.1 RAG

建议具备基于资料检索的能力：在资料较长时检索相关内容，并把来源上下文用于出题与评价。资料较短、能够合理放入模型上下文时，也可以直接使用所选内容。

具体采用关键词检索、向量检索、混合检索或其他方法，应根据资料类型、检索质量、成本和实际验证决定。当前不预设某种方案一定更优，也不把 RAG 等同于评价准确性的保证。

### 7.2 知识图谱

知识图谱可以用于表达知识点之间的前置、关联或跨资料关系；如果以后需要围绕这些关系安排检验，可再评估引入。

建议首版不把知识图谱作为必要前提。资料、章节、问题、回答、评价及来源的关联可以先用普通结构化记录表达。知识点列表或章节目录也不自动等同于知识图谱。

**待确认**：是否需要跨资料的前置知识关系、关系可视化或基于图谱的检验；图谱的来源和人工纠错如何处理。

### 7.3 Java、Spring AI 与 Python 的职责比较

**用户已确定**：Windows 桌面应用及主要服务在本机运行；采用 Java＋Spring AI 负责业务和 Agent，Python 主要承接本机 MinerU 解析。

| 部分 | 已确定方向或待验证职责 |
| --- | --- |
| 桌面应用 | 安装、展示交互并管理本机服务；具体桌面框架未确定。 |
| Java＋Spring AI | 负责项目和业务状态、Agent 编排、模型调用、工具调用、检验进度及数据提交；业务规则和权限由应用明确实现。 |
| Python＋MinerU | 主要承担本机文档解析，可通过受控的本机进程或服务与 Java 协作；具体协议和进程方式待设计。 |

用户熟悉 Java，并学过 Python 的 LangChain 和 LangGraph；本项目选择 Spring AI 作为 Java Agent 技术方向，不要求同时再实现一个 Python Agent。“Java 负责业务和 Agent”不等于整个产品完全没有 Python：本机 MinerU 仍需解决相应运行环境、进程或服务及打包。

应先验证 Spring AI 动态多服务商配置、工具调用与外部 MCP、F10 的预算和停止条件，再验证本机 MinerU 解析与打包、实时语音对接。框架提供工具调用能力，不自动保证项目的追问上限、数据一致性或语音兼容性。

## 八、非功能需求

以下为建议，具体指标需要在技术设计和实际测试中确定：

- **准确与可解释**：问题和判断应能回溯到有效依据；错误或不确定情况应如实展示。
- **可用性**：用户能看懂当前是在出题、等待回答、检索、核验还是生成反馈。
- **可靠性**：解析、检索、模型或网络失败时明确提示；已经接受的用户回答不应被静默丢弃。
- **可恢复性**：长时间对话中断后，用户能够回看已保存的记录，并按产品设计继续或重新开始。
- **隐私与隔离**：资料和记录的访问范围由应用控制；外部搜索和远程模型调用应有清晰的数据使用边界。
- **可验证性**：能够区分示例、模拟、真实调用结果和尚未核验的推断。
- **适用性**：对于需要多种表达和多种合理观点的学科，不以关键词命中率代替理解判断。

F10 已给出单次回答处理回合的初始执行预算；其他性能目标、并发量、离线能力、系统平台及无障碍要求尚未量化。

## 九、建议的首版范围

本章仅为开发排序建议，不代表用户已确认最终版本划分。

### 9.1 建议优先完成

1. 支持不超过 10 MB 的 Markdown、PDF、Word 资料及其中扫描页、公式、表格、图表和图片，解析并提取知识点待办清单。
2. 按重要程度和掌握情况安排问题，执行每个知识点“1 个主问题＋最多 2 次追问”的默认上限。
3. 使用事先列出的必备要点判断覆盖率，并结合资料检索、按需联网核验展示判断依据。
4. 用户可以主动提问、指出判断问题或结束检验。
5. 保存基本检验记录，展示清单进度与回答时间，并支持回看。
6. 按回合执行预算处理模型与工具调用，在超限或失败时保留回答。
7. 提供可选资料或无资料的模拟面试对话及结束后的复盘。
8. 提供 Windows 桌面安装及本机数据保存、用户模型配置和可开关的联网搜索工具；题目与依据支持溯源。

### 9.2 建议随后确定或迭代

- 日常语音输入、语音播报和面试实时语音均为已确认能力；具体版本顺序、服务和实时细节待确定。
- 复测计划和更完整的历史统计；定时提醒按用户决定暂缓。
- Markdown 总结、HTML／Markdown／PDF 导出、记忆和三类提示词均需保留；与首版的具体划分待确定。
- 跨资料知识关系、知识图谱及可视化。
- 自进化与 Skill 沉淀需保留；外部 MCP、Skill 和工具接入作为后续扩展，具体阶段待确定。

| 本地数据与模型 | 曾确定资料和业务数据本地保存，远程模型只接收任务需要的上下文。 | 已确认本机保存、界面配置及密钥加密；备份恢复给出建议默认值，服务适配仍待验证。 |
| Markdown 总结与文件工具 | 曾提出自动生成可编辑的 Markdown，总结和资料使用受控文件工具。 | 已确认保留 Markdown 总结；生成时机、编辑方式与文件工具权限待定。 |
| 多格式导出 | 曾提出导出 PDF、Word、Markdown、HTML。 | 已确认导出 HTML、Markdown、PDF；本轮不将 Word 作为导出要求。 |
| 记忆与提示词 | 曾提出用户可查看、修改记忆，用户或项目提示词可覆盖默认提示词。 | 已确认系统安全优先，项目提示词可覆盖个人提示词，项目隔离且冲突交用户处理；加载及编辑细节待定。 |
| 定时提醒 | 曾提出站内或桌面提醒、定时邮件及关机后云端发送已同步提醒。 | 一般学习提醒仍暂缓；另按用户新需求提供本地 API 密钥定期检查提醒。 |

| 课程、试用与求职展示 | 曾将课程项目、少量朋友试用和展示 Java 后端、Agent 及一定全栈能力作为目标。 | 用户明确这是同一个项目，交付与验收不分成三套。 |

## 十一、建议验收场景

以下是对已讨论方向的行为验收建议；已确认能力的验收随其进入的版本执行，具体版本划分尚未全部确定。

| 编号 | 场景 | 建议通过条件 |
| --- | --- | --- |
| A01 | 用户提供可处理的资料 | 能看到处理状态并选择检验范围；解析失败或部分失败时不会显示为完整成功。 |
| A02 | 基于资料开始检验 | 知隙提出与所选范围相关的问题，并能在评价时关联可靠的资料依据。 |
| A03 | 用户换一种方式正确表达 | 系统评价其实际含义，不仅因为未出现预设关键词而判错。 |
| A04 | 回答不完整或有歧义 | 反馈说明已覆盖和未说明的部分，必要时追问或标记待确认。 |
| A05 | 用户回答包含资料外的信息 | 系统不把“当前未检索到”直接当作错误；可按需联网查找并区分外部依据。 |
| A06 | 用户资料与外部资料冲突 | 展示双方可核对来源和差异；无法确定时不捏造最终结论。 |
| A07 | 搜索或网页读取失败 | 明确说明外部核验未完成，不编造链接或来源内容。 |
| A08 | 用户质疑评价 | 用户可查看来源和自己的回答，并补充说明或纠正；历史如何保留符合最终约定。 |
| A09 | 结束并回看检验 | 可回看已保存的问题、回答、判断和依据，并区分未检验内容。 |
| A10 | 模拟面试 | 系统能够进行连续问答和必要追问，并基于实际回答提供复盘。 |
| A11 | 工具遇到资料或网页中的指令性文本 | 应用的实际权限边界不由该文本改变；不可访问的资料和工具仍被程序拒绝。 |
| A12 | 语音能力 | 日常语音输入、播报和面试实时语音分别验收；实时语音应验证真实的持续语音交互，打断及具体时延按后续确定的标准验收。 |
| A13 | 生成知识点清单 | 从所选资料提取可查看、调整并关联来源的知识点；解析或提取不完整时明确提示未处理范围。 |
| A14 | 动态安排问题 | 能结合重要程度和用户回答表现调整顺序；未检验不显示为不会，其他待检验项目不会因反复追问少数知识点而长期被忽略。 |
| A15 | 限制单个知识点的追问 | 一次检验最多 1 个主问题和 2 次追问；达到上限仍未通过时保留待办状态并转到同主题下一知识点，同一轮不自动重置计数。 |
| A16 | 提前达到完成标准 | 用户独立、正确覆盖全部预先列出的必备要点，且依据充分、无关键错误时，知识点可提前完成，无需凑满追问次数。 |
| A17 | 辅助回答与证据不足 | 仅复述知隙给出的答案不能直接算作独立掌握；无必备要点、资料不足或来源冲突尚未解决时不能按 100% 通过。 |
| A18 | 清单完成与范围 | 只有当前范围内至少一个知识点且全部达到本轮完成标准时显示清单完成；跳过和筛选视图为空不能冒充完成，排除项及未处理范围清晰展示。 |
| A19 | 模型与工具调用预算 | 一次回答处理回合的模型调用不超过 4 次、Agent 工具调用不超过 5 次，其中联网搜索不超过 2 次；计数包含失败调用。 |
| A20 | 超时、预算耗尽与手动重试 | 在预算用尽且判断尚未完成时停止派发超额请求、保留用户回答并提示判断未完成；预算内恰好完成可正常返回。手动重试同一回答不增加追问或作答次数，迟到结果不能覆盖较新的状态。 |
| A21 | 已完成记录与再次检验 | 达到标准的知识点移出待办主视图但仍可回看原回答和依据；用户主动再次检验时建立新记录并重新计数。 |
| A22 | 资料格式与 MinerU | 实际选择 Markdown、PDF、Word 样例完成读取或解析和知识提取；首版必须验证扫描件及文档内公式、表格、图表、图片。MinerU 的本机运行和 Word 格式兼容性按选定版本验证。 |
| A23 | 无资料和有资料面试 | 分别验证仅设置岗位与场景即可开始问答，以及选择已上传资料进行面试；无资料时不伪称存在用户资料依据。 |
| A24 | 日常辅助与面试限制 | 日常检验可以请求提示或临时解释，记录辅助痕迹并标记不熟练；面试模式不提供提示或临时解释。 |
| A25 | 桌面本地运行 | 在目标 Windows 环境安装、启动应用及本机服务；资料和检验记录实际保存于本机，退出重启后的保存行为符合最终设计。 |
| A26 | 模型服务配置 | 用户可在界面配置并管理服务商、模型名称、Base URL 和 API 密钥；测试所声明支持的协议和连接，普通日志或导出中不出现明文密钥。 |
| A27 | 联网搜索开关 | 开启时可以按需调用自建搜索工具；关闭时该工具不被调用，搜索失败或不可用明确提示。 |
| A28 | 总结与导出 | 能自动生成真实、可编辑的本地 Markdown 总结文件，按用户选择导出可打开的 HTML、Markdown 和 PDF；自动生成时机及来源关联按最终设计验收。 |
| A29 | 记忆与提示词 | 可以管理记忆和三类提示词；系统安全优先、项目可覆盖个人、项目隔离，实质冲突产生候选并由用户处理，不能静默覆盖长期内容。 |
| A30 | Skill 自进化 | 可将经核实的反馈整理为候选 Skill，展示来源与验证记录，人工确认后启用，并可停用或回退；不能把候选直接宣称为已验证有效。 |
| A31 | 外部扩展（进入对应版本时） | 已配置的外部 MCP、Skill 和其他工具可按最终确定的协议、格式与权限规则接入或停用，Agent 工具调用受到预算限制。 |
| A32 | 资料大小与图片范围 | 按界面公布的 10 MB 计量规则验证边界及超限提示；接收 Markdown、PDF 和 Word 并处理其中图片，不将 PNG、JPG 等独立图片当作首版上传格式。 |
| A33 | 解析质量与完整性 | 使用人工对照原文的样例统计文字、公式、表格和图片／图表错误或遗漏；超过 10 页的文档不得因调用工具的默认页数而静默漏页。 |
| A34 | 外部拓展与题目溯源 | 用户可选择拓展题；能够区分资料内、资料外及无可核验来源的题目，展示可核对的资料或外部来源。关闭拓展题不关闭已允许的联网核验。 |
| A35 | 禁止中途自由切换 | 未完成或退出当前主题时，用户不能手动跳到其他知识点、资料或项目；达到追问上限未掌握时，系统能标记待巩固并自动进入同主题下一项；退出后进度可恢复。 |
| A36 | 回答时间 | 每道主问题及追问可查看用户作答时长，系统处理或网络等待不混入；文字与语音时间的计量方式可解释，不单凭时间判定掌握。 |
| A37 | 冲突与项目隔离 | 用户和项目指令冲突按已定优先级处理并产生候选；记忆冲突不静默覆盖、等待用户处理；不同项目资料和记忆不自动相互泄露。 |
| A38 | 密钥加密与检查提醒 | API 密钥加密保存且不落入普通日志或默认备份；按用户配置的周期在应用运行时提示检查，不伪称已自动验证密钥状态。 |
| A39 | 本地备份与恢复 | 按最终确定策略完成一致性备份并在隔离目标实际恢复；删除应用资料不删除用户原始文件，备份和密钥排除规则清楚可见。 |
| A40 | 安装与硬件验收 | 在干净 Windows 环境检查安装、启动、升级与卸载，并在真实机器记录本机解析耗时、资源占用和界面响应；安装包及模型文件策略符合最终选择。 |
| A41 | 统一交付 | 课程、用户试用和求职展示使用同一产品与验收基线，交付内容不人为拆成三套项目。 |
| A42 | 文档解析后台响应 | 在典型 CPU 和可用 GPU 的真实设备上，对多页扫描件和接近 10 MB 的复杂文件记录解析耗时、资源占用、界面响应、取消和失败反馈；具体性能通过阈值根据实测确定。 |

建议准备覆盖多个学科、不同表达、资料缺漏、版本冲突和开放性回答的人工核对样例，分别检查资料解析、检索、引用和最终判断。模型生成的评价不能单独作为自身效果已经成立的证据。

## 十二、待确认问题

1. 解析质量的样例规模、文字／公式／表格／图片及图表的具体通过阈值如何确定？10 MB 的字节计量及 Markdown 附图总量上限如何说明？
2. 资料外拓展题的默认开关状态、来源展示时机及外部服务不可用时的具体处理如何确定？
3. 退出主题后的恢复交互如何设计？计时中断或语音打断时如何准确记录回答时间？
4. 除已确认的回答时间、必备要点覆盖率和清单进度外，是否展示总时长、追问次数、独立／辅助作答次数或其他分数？
5. 已选择 Java＋Spring AI 负责业务和 Agent、Python 主要承接 MinerU；具体依赖版本、Java／Python 协议、多服务商适配及工具预算如何验证？
6. 日常语音输入、语音播报与面试实时语音分别进入哪个版本？选择外部、本地还是混合服务？实时会话是否支持打断，以及时延如何验收？
7. 本机目录、音频保留、备份和 API 密钥检查周期已给出建议默认值；具体实现、用户可修改范围和恢复测试如何落实？
8. 系统安全基线和可编辑提示词如何分离？冲突候选如何展示、合并或保留？项目与个人记忆何时加载？
9. Skill 验证样例、启用范围和外部格式采用哪组选项？外部 MCP 和其他工具进入哪个版本？
10. 自建搜索工具采用外部搜索 API 还是自部署聚合服务？由谁配置密钥、承担费用，开关默认值是什么？
11. 安装包是包含 MinerU 模型文件，还是在首次使用时引导下载？虚拟机及真实机器的配置矩阵和性能目标如何确定？
